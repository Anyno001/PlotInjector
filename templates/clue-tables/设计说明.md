# 线索推进配套表格：设计说明

本文件说明配套表格的用法和设计理由。

表格格式以 **shujuku 8.9.2 自带模板**为准：
- 表头首列是 `row_id`；
- `sourceData` 包含 `note`、四个节点规则（`initNode` / `deleteNode` / `updateNode` / `insertNode`）和 `ddl`；
- `mate` 的 version 为 1。

模板已经通过 shujuku 自己的导入校验，包括结构、DDL 与表头一致、row_id 规范化无阻断，JSON 和 SQLite 两种存储模式都检查过（原开发阶段在数据库源码侧验证；本仓库回归测试见 `tests/clue-template.test.mjs` 和 `tests/template-story.test.mjs`）。

## 现在的推荐用法：平时的表 + 三张线索表

剧情注入器执行页「表格绑定」卡片里有 **「生成线索模板…」**：

1. 读当前聊天正在用的数据库模板（官方接口 `getTableTemplate`），和正在运行的表格核对，对不上（比如读到的是全局模板）就不生成。
2. 在它的基础上：
   - 加入线索控制表、关键事实表、知情表。线索表还不存在时，带上大纲里的事实和知情预建行，标签和登记口径由你在预览里填写。
   - 「全局数据表」和三张线索表改成每楼更新、放在同一组。
   - 「重要角色表」加「剧情身份」「当前动向」两列。
   - 「重要角色表」「任务与事件表」「选项表」：只有原文和官方默认一字不差时，才替换与线索主线冲突的初始化句，然后在说明末尾追加一段附加规则。
3. 预览全部改动和需要注意的地方。确认后用 `importTemplateFromData(…, { scope: 'chat', dataMode: 'seed' })` 只导入到当前聊天。
4. 导入成功才写插件的表格绑定。

不会删除任何表或列，已有表格数据保留。认不出的表（改过名、改过列）原样不动，只在预览里列出来。重复生成不会叠加规则。

**已经有线索表的聊天**（比如第二段主线）：生成模板更新结构和规则，不依赖种子行给已有数据表补行。场景目录由运行时同步，新模板则直接写入种子行。新事实可用「按大纲补预建行…」；多线项目开线时也会补齐已有中性标签的预建行。

表格的定义只有一份：插件源码 `src/core/clue-template.js`。随包的模板文件也由它生成。

## 线索表与默认表的调整

| 表 | 作用 | 规模 | 正文能否看到 |
|---|---|---|---|
| 线索控制表 | 当前场景编号、场景目录（主线开关在执行页，故事时间读全局数据表） | 固定 1 行 | 不导出（插件读取，目录供填表识别） |
| 关键事实表 | 需要控制进度的发现，用状态区分 未获得 / 已核实 / 存疑 | 卡作者**预建**，固定行数 | 不导出（插件按需投影） |
| 知情表 | 关键事实 × 关键角色的获知方式 | 卡作者**预建**，固定行数 | 不导出 |
| 全局数据表（官方默认） | 改为每楼更新，故事时间从这里读 | 1 行 | 原行为 |
| 重要角色表（官方默认） | 加「剧情身份」「当前动向」两列；初始化只建正文里出现的人 | 随人物登场增加 | 原行为（按姓名触发 + 已登场索引） |
| 任务与事件表（官方默认） | 不再按设定预写主线；只记正文里接下的委托和目标 | 随任务增加 | 原行为（常驻） |
| 选项表（官方默认） | 选项只涉及主角已经知道的地点、人物和线索 | 1 行 | 原行为（常驻） |

旧版配套模板里我们自己改过的重要角色表（身份说法 / 身份核实）和纪要表（关联编号 / 未完成事项）不再使用：插件从来不读这些列，实测里也基本是空的或重复的。已经用旧模板的聊天不受影响。

## 关键设计决定

1. **关键事实表和知情表都预先建好行，填表只改格子，不新增行**。规模由卡作者定（关键事实数 × 关键角色数），不会无限增殖。重复记录也基本不会出现，因为没有新行可加。预建行只写编号和中性标签（如「钱箱撬痕」），**不写答案**，不泄露剧透。
2. **状态值是固定的几个词**，写进了 DDL 的 CHECK 约束（SQLite 模式下会强制校验）。填表模型只需要从几个词里选一个，比写自然语言稳定。
3. **「在场不等于知道」写进了知情表的说明**，这是这一档模型最常犯的错。
4. **「存疑」和「已核实」分开**：说法、传闻记为「存疑」。「事实: X」条件把存疑也算作已经出现（拿到证词就能往下走）；门槛要求被证实时，用「核实: X」条件，只认已核实。（2026-11-08 雾港实测后改：原来存疑不满足「事实」，拿到证词的节点永远完不成。）
5. **人物身份的说法和核实**：「他说自己是记者」是已经发生的发言；「他是记者」是否属实，是另一回事。现在写在重要角色表的「剧情身份」里（谁在第几楼怎么说，被核实或推翻时追加），需要卡住进度的身份谎言放进关键事实表用「存疑」记录。
6. **关键事实表和知情表默认不导出到正文**。正文需要的已确认事实，由插件在焦点场景里投影出来，并带上「谁知道」。这样知情差异不会因为表格常驻可见而失效。
7. **纪要表用官方原版**：旧版加过「关联编号」「未完成事项」，插件从不读取，实测基本是空的，已取消。
9. **说明按列名写，不写「列1、列2」**：数据库给填表模型看的列头编号从 0 开始，文字里的序号容易和操作索引错开一位。SQL 示例只用占位符，不放具体剧情。
10. **场景格可以写「无」或「离场」**：玩家明确离开调查时写离场值，插件停止当前场景材料；空白不等于明确离场。地点相同也可能已经在做别的事，按实际活动判断。
11. **依据规则写进每张线索表**：官方数据库的剧情推进会把规划结果写回用户消息，填表读到的「用户发言」里可能有「准备去查账本、会找到那页」这类计划。所以三张线索表都写明：只按正文里实际发生的事填写，计划和打算不算，并附一个反例。
12. **关键事实表有「登记口径」列**：写「正文出现什么才算取得这一项」，不写答案。填表靠它把正文里的结果对上编号（官方数据库不会把插件的逐楼编号对照带进填表请求）。插件的「按大纲补预建行」会从大纲的「记录」生成草稿；如果记录里出现了答案里的词，就不预填，留给作者改写。
13. **场景编号对照放在线索控制表的说明里**：官方填表只展开当前任务的目标表，单独一张场景表不一定和控制表在同一个请求里。对照只有编号、入口、地点，和正文看到的入口同级；长主线只放当前几个阶段。
8. **三张线索表每楼都填**：线索控制表、关键事实表、知情表决定下一楼正文拿到什么材料，所以设成每 1 楼 AI 回复填一次、不跳楼，放在同一组（groupId=0），一次填表一起更新。重要角色表（groupId=2）和纪要表（groupId=1）不需要实时，跟随用户的全局频率。官方数据库按「组 + 频率 + 跳楼 + 楼层范围」合并填表请求，频率不同的表就算放进同一组也会拆成两次请求，所以人物表单独一组。代价：用户的全局频率大于 1 时，线索表的填表是在原有填表之外单独发的请求。

## 对填表模型能力的预期（以 DeepSeek 4.1 Flash 级别为参照）

- **一般能做好的**：在固定选项里选值，只改已有行，照抄编号，按「正文写没写出来」判断是否发生。
- **容易出错的**：
  - 把同场的人记成知情。模板说明里已经写明，插件的核验和人工维护也能兜底。
  - 把说法记成核实。用「存疑 / 未核实」两档区分开，出错时影响的是「核实」条件，不会让角色变成「不知道」。
  - 编号认错。靠「登记口径」列和中性标签对号；插件对「填表里没提供过候选、却第一次被记为已核实」的事实会提示检查。
  - 写错「当前场景」。控制表说明里的场景编号对照只有编号、入口、地点，填表只能从中照抄。有并行节点时，焦点就是靠这一格确定的。
  - 把用户消息里的计划当成已发生。依据规则和反例写在每张线索表里。
- **出错时怎么办**：执行页可以人工确认、撤销事实；表格可以直接改；回滚时状态一起回滚。

## 卡作者使用步骤

1. 进入要玩的聊天（新聊天，或者已经玩了一段日常的聊天都可以）。
2. 剧情注入器 → 执行页 → 推进方式选「线索推进」。
3. 「表格绑定」卡片 →「生成线索模板…」：看一遍改动清单和需要注意的地方，给每个事实填上中性标签和登记口径，然后导入。
   - 标签要中性，比如不要把「认罪」这样的未来结果写成标签，填表模型能看到这些行。
   - 标签也要指向被追踪的那件东西，不要写成场景里一眼就能看到的东西。实测：标签写「仓库外的痕迹」，正文只看清了拖痕、还没找到口径要的物件，知情表就把两个人都记成了「亲见」。改成「拖痕旁的物件」更准确。
   - 身份本身就是谜底的人物，等他在正文登场后再建行，或者先用公开的称呼。
4. 每个发现都写上「记录」字段（给作者和插件生成登记口径用），例如「主角实际读到这页时记 F_ledger 为已核实」。不要在记录里写答案。
5. 第二段主线：写好新一卷后，再点一次「生成线索模板…」更新场景对照，然后用「按大纲补预建行…」补新事实的行。补的行写在当时那一楼上，之后几楼内对线索表做「手动填表」重填，可能会清掉它们，补完请检查一次。

## 实测得到的注意事项（真实酒馆 · 官方数据库）

- **登记口径要在模板里一次写好，不要开局后再改。** 开局后通过数据库接口改单元格，改动会挂在当时最后一条 AI 消息上；之后点「手动填表」，数据库会清掉最近几楼上这些表的记录，再让模型重填（事务式重填），手动改过的格子就回到了模板里的原值。需要改口径时，改模板后用新聊天开局。
- **口径写清：在哪里、谁、要对上的是什么、哪些不算。** 只写「相关传闻」，模型会把别的传闻也对到这个编号上。一个编号只追踪一件能单独揭示的事，按那件关键东西判定（比如「捡到拖痕旁的物件」），不要按「走到尽头」这种过程判定。
- **重新生成（swipe / regenerate）最后一楼后，自动填表可能不跑。** 数据库按「这一楼有没有填过」决定要不要填，不看回复内容变没变；被替换的那个版本已经填过，新版本就不会自动填。重新生成后请手动点一次填表。
- **当前场景容易被误写**：模型可能把「看到、记下」当成「到了、开始做」。控制表说明里已经加了反例；误写时在执行页对那个节点点「离开这个调查」，或者把焦点改回去。

## 和已有模板合并

「生成线索模板」就是做这件事。手动合并时，至少要有三张线索表，绑定只引用它们；默认表的调整都是可选的。
